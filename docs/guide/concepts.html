Concepts개념

Two directions, one boundary두 방향, 하나의 경계

Every design decision in this project splits along the direction of the call. The two directions are orthogonal and use entirely different mechanisms.이 프로젝트의 모든 설계는 호출 방향을 따라 갈린다. 두 방향은 직교하며 메커니즘이 완전히 다르다.

01Downcall: Kotlin → Python다운콜: Kotlin → Python

The CPython Stable ABI is declared once, in EmbedAPI.kt, as about 330 expect functions. Each platform supplies the actual: Panama FFM with invokeExact on the desktop JVM, JNI registered through RegisterNatives on Android, cinterop on Kotlin/Native, and an Emscripten build on wasm.CPython Stable ABI 를 EmbedAPI.kt 에 약 330개의 expect 함수로 한 번 선언한다. 플랫폼마다 actual 을 둔다: 데스크톱 JVM 은 invokeExact 를 쓰는 Panama FFM, Android 는 RegisterNatives 로 등록한 JNI, Kotlin/Native 는 cinterop, wasm 은 Emscripten 빌드.

On top sits a typed object model, sketched by the maintainer in python_for_kotlin_binding.mermaid: PyObject at the root, PyType, PyException as a Throwable, and collections that implement the Kotlin interfaces.그 위에 타입이 있는 객체 모델이 있다. 메인테이너가 python_for_kotlin_binding.mermaid 에 스케치한 대로, 최상위에 PyObject, 그리고 PyType, Throwable 인 PyException, Kotlin 인터페이스를 구현하는 컬렉션들이 있다.

02Upcall: Python → Kotlin업콜: Python → Kotlin

Kotlin/Native has no useful reflection and a GraalVM native image is a closed world, so nothing is looked up at run time. At build time, a KSP processor (for your sources) and the Gradle plugin's artifact walker (for prebuilt jars) generate a function table. Python reaches it through one entry point per platform, wrapped in generated proxies that read like ordinary Python.Kotlin/Native 에는 쓸 만한 리플렉션이 없고 GraalVM 네이티브 이미지는 닫힌 세계이므로, 런타임에 아무것도 조회하지 않는다. 빌드 타임에 KSP 프로세서(내 소스)와 Gradle 플러그인의 아티팩트 워커(빌드된 jar)가 함수 테이블을 생성한다. Python 은 플랫폼마다 하나인 진입점으로 그 테이블에 닿고, 평범한 Python 처럼 읽히는 생성된 프록시가 그것을 감싼다.

Exposure is a blacklist: every public declaration is registered, and @PythonInternal opts one out.노출은 블랙리스트다. 모든 public 선언이 등록되고, @PythonInternal 로 제외한다.

03Lifetime across the boundary경계를 넘는 수명

CPython counts references; Kotlin collects garbage. A Kotlin wrapper takes one reference and gives it back when the wrapper is collected (a Cleaner, or a PhantomReference path on older Android). Cycles that run through a Kotlin proxy are made visible to Python's cyclic GC, so they are collected too.CPython 은 참조를 세고, Kotlin 은 가비지를 수거한다. Kotlin 래퍼는 참조 하나를 잡고, 래퍼가 수거되면 돌려준다 (Cleaner, 구형 Android 에서는 PhantomReference 경로). Kotlin 프록시를 지나는 순환도 Python 의 순환 GC 에 보이게 하므로 함께 수거된다.

04Threads스레드

Every C API call holds the GIL. Parallelism will come from free-threaded CPython (3.14t works on desktop with -PpythonFreeThreaded=true; the default is still the GIL), not from sub-interpreters: extensions that do not declare multi-interpreter support fail to import in a sub-interpreter.모든 C API 호출은 GIL 을 잡는다. 병렬성은 서브 인터프리터가 아니라 free-threaded CPython(desktop 에서 -PpythonFreeThreaded=true 로 3.14t 동작, 기본값은 여전히 GIL)에서 온다. 멀티 인터프리터 지원을 선언하지 않은 확장은 서브 인터프리터에서 import 가 실패하기 때문이다.

05Names이름

A Kotlin package is a Python module under the same name: androidx.compose.ui in Python is androidx. The binder never renames a namespace. Pythonic layers like pythonx are real Python packages that import those modules and reshape them — they live in their own repository.Kotlin 패키지는 같은 이름의 Python 모듈이다. Python 의 androidx.compose.ui 는 androidx 다. 바인더는 네임스페이스를 바꾸지 않는다. pythonx 같은 파이써닉 계층은 그 모듈을 가져와 다듬는 실제 Python 패키지이고, 자기 저장소에 있다.
