## 1. 동기

Rust 와 TypeScript 가 AI 에이전트와 잘 맞는 이유는 언어 자체보다 **컴파일러가 돌려주는 피드백 루프**에
있다.

- 에러가 위치와 원인을 짚는다.
- 타입이 곧 문서다. 에이전트가 읽을 계약이 코드 안에 있다.
- "컴파일된다" 가 정합성의 기준선이 된다.

파이썬에는 이 루프가 없다. 그래서 AI 가 코드를 쓰는 비중이 커질수록 파이썬은 불리해진다.
TypedPython 의 목표는 **새 언어를 만들지 않고, 파이썬 문법 그대로 이 루프를 갖추는 것**이다.
여기에 두 가지를 더한다.

1. 타입이 확정된 코드는 **네이티브로 컴파일**해서 앱에 싣는다. PythonMultiplatform 의 배포 목표인
   "파이썬 부분도 컴파일된 채로 들어간다" 와 같은 자리다.
2. GPU 커널을 **별도 언어(CUDA, Metal Shading Language, Mojo) 없이** 파이썬 서브셋으로 쓴다.

## 2. 원칙

### 2.1 유효한 파이썬만

새 문법·키워드를 만들지 않는다. TypedPython 코드는 **수정 없이 CPython 에서 그대로 실행돼야 하고**,
그 상태가 디버깅 모드다.

모조는 `fn` 같은 새 문법을 넣으면서 "파이썬 슈퍼셋" 약속에서 물러섰다. 기존 도구(IDE, 린터, 테스트
러너, CPython 자체)와의 호환을 잃는 순간 "파이썬을 남게 한다" 는 목표와 어긋나므로 그 길을 피한다.

### 2.2 코틀린식 계약

**시그니처는 명시하고, 지역은 추론한다.**

- Rust/TS 의 관례와 같다. 공개 경계에 타입이 적혀 있어야 에이전트와 사람이 계약을 읽는다.
- Pyrefly 가 파라미터를 추론하지 않는 것과도 맞는다 (§4.1).
- 코틀린의 추론이 되는 이유는 추론기가 강해서가 아니라 **언어가 재할당을 금지하기 때문**이다.
  TypedPython 은 같은 효과를 **금지 목록**으로 얻는다 (§3).

### 2.3 검사는 기본, 컴파일은 opt-in

축이 둘이다. **검사**는 PythonMultiplatform 빌드의 기본 동작이고, **컴파일**은 표시한 코드에만
적용된다.

| 등급 | 대상 / 표기 (안) | 보장 | 출력 |
|---|---|---|---|
| 0 | 서드파티 패키지 (의존성) | 없음 — 검사하지 않는다 | 바이트코드 (pypackpack 이 받은 그대로) |
| 1 `checked` | **사용자 프로젝트의 파이썬 코드 전부 — 기본값** | 빌드 타임 타입 오류, `Any` 유출 0 (§4.2) | 바이트코드 |
| 1 `compiled` | `@compiled` (내장 이름, import 없음) 또는 모듈 선언 `# typedpython: compiled` | `checked` + §3.1 금지 목록 | C 확장 모듈 |
| 2 `kernel` | `@kernel` | 객체·힙 할당 없음, 고정 dtype | SPIR-V / MSL / WGSL / PTX |

- **사용자 코드는 표시하지 않아도 검사된다.** 타입 오류가 있으면 Kotlin 컴파일 에러처럼 빌드가
  실패한다. TS 의 `strict` 기본값과 같은 위치다.
- **서드파티는 검사하지 않는다.** 그 대신 사용자 코드가 서드파티를 부르는 지점에서, 그 패키지의
  스텁(`.pyi`, `py.typed`)이 있으면 그것을 믿고 없으면 그 경계를 `Any` 출처로 표시한다. `Any` 가
  사용자 코드 안으로 퍼지면 그 지점에서 에러가 난다 (§4.2).
- **컴파일은 선택이다.** `checked` 코드는 타입이 이미 확정돼 있으므로 `@compiled` 를 붙이는 비용은
  §3.1 금지 목록을 지키는 것뿐이다.
- 등급 사이의 경계에서는 **검사된 변환**이 일어난다.

## 3. 등급 1 — checked / compiled

### 3.1 금지 목록

`compiled` 코드에서는 다음을 컴파일 에러로 다룬다. `checked` 코드에서는 경고로 보고한다 — 기본 검사가
기존 파이썬 관용구를 막아 채택을 해치지 않게 하면서, `@compiled` 로 옮기기 전에 무엇을 고쳐야 하는지
미리 보이게 하려는 것이다. (이 경고/에러 구분은 제안이다 — §8.)

- 변수의 타입 재할당 (`x = 1` 뒤 `x = "a"`)
- `eval` / `exec`, 이름을 문자열로 만드는 `getattr`/`setattr`
- 런타임 클래스 변경, 몽키패칭 (`compiled` 클래스는 암묵적으로 `@final` + 고정 슬롯)
- 원소 타입이 섞인 컨테이너 (`list[int | str]` 는 명시하면 허용, 추론으로 섞이는 것은 거부)

이것이 코틀린의 `val`/`var` 보장을 파이썬 문법 안에서 재현하는 방법이다.

### 3.2 수치 타입

- 일반 `int` 는 **임의 정밀도 의미를 유지**한다. 조용히 64비트로 바꾸지 않는다.
- 고정폭이 필요하면 `i32`, `i64`, `f32` 같은 타입을 쓴다. `Annotated` / `NewType` 기반으로 정의해
  **유효한 파이썬이면서 CPython 에서도 동작**하게 한다.
- 고정폭 정수의 오버플로 의미(래핑 / 디버그 빌드에서 검사)는 미결 (§8).

## 4. 등급 1 의 구현

### 4.1 프론트엔드 — Pyrefly

Meta 의 Pyrefly 를 타입 추론기로 쓴다.

- Rust 구현이라 빠르고, 대규모 코드베이스(Instagram, PyTorch, JAX)에서 쓰이고 있다.
- 지역 변수와 반환 타입을 추론하고, `pyrefly infer` 로 애노테이션을 생성할 수 있다.
- 빈 컨테이너 타입을 첫 사용처로 정하는 등 실용적인 규칙을 갖고 있다.

**포크하지 않는다.** 처음에는 CLI 와 기계 판독 가능한 출력 수준에서 붙이고, 라이브러리 임베드는
API 안정성을 확인한 뒤로 미룬다.

### 4.2 건전성 게이트 — TypedPython 고유의 일

타입 체커와 컴파일러는 목표가 반대다.

- 타입 체커: 확신이 없으면 `Any` 로 물러서는 것이 미덕이다. 거짓 경고를 안 내야 하니까.
- 컴파일러: `Any` 를 만나면 최적화를 못 한다. 그것은 결함이다.

그래서 Pyrefly 를 "통과" 한 코드가 "컴파일 가능한" 코드와 같지 않다. 이 간극을 메우는 층을 둔다.

    사용자 코드(`checked` · `compiled`)에서
      Any · 미해결 타입 · object 가 섞인 유니온   → 경고가 아니라 에러
      시그니처에 애노테이션 없음                   → 에러
      §3.1 금지 목록 위반                          → `compiled` 는 에러, `checked` 는 경고

**이 게이트만으로도 독립적인 가치가 있다.** 컴파일러가 없어도 "사용자 코드에는 `Any` 가 없다" 는
보장이 생기고, 그것이 AI 친화적 피드백 루프의 핵심이다. 이후 모든 단계가 이 게이트를 전제로 한다.

### 4.3 백엔드 — 자체 typed IR → C (결정 2026-10-03, #41)

**Cython 은 쓰지 않는다** (사용자: "Cython 의존 별로야. 2단계로 바로 진행하도록 해"). Cython 경로
(PR #39)는 닫았고, 거기서 검증된 의미 보존 규칙만 IR 계약으로 옮겼다.

    소스 ─ Pyrefly 추론 ─▶ frontend ─▶ typed IR ─▶ verify ─▶ cgen ─▶ C ─▶ 플랫폼 C 컴파일러 ─▶ 확장 모듈
                                        (ir.py)     (증명)     (CPython C API + tp_runtime.h)

- **IR 이 계약이다** (`typedpython/ir.py`). 각 노드는 CPython 동작으로 정의된다: 검사되는 i64 산술과
  오버플로 시 deopt(인터프리터 재실행), 파이썬식 floor 나눗셈·나머지, 정확한 int/float 비교, 리스트식
  인덱싱, `math` 모듈의 예외. C 런타임 API 는 `typedpython/runtime/API.md` 에 고정했다.
- **왜 C 인가, LLVM 이 아니라.** 모든 타깃에 C 컴파일러가 이미 있다(clang, NDK, Xcode) — 새 의존이 없다.
  CPython C API 가 C 이고, 플랫폼 디버거가 그대로 쓰인다. 타입이 확정된 스칼라·배열 코드에서 중요한
  최적화(인라이닝, 벡터화)는 C 컴파일러가 이미 한다. IR 이 안정 계층이라 LLVM 백엔드는 나중에도 붙일 수 있다.
- **왜 Rust 가 아닌가.** 파이썬의 별칭과 공유 변경은 Rust 소유권에 맞지 않아 생성 코드가
  `Rc<RefCell>`/`unsafe` 로 채워지고, 앱 빌드마다 Rust 툴체인 비용이 붙는다(사용자 확정).
- **모듈 모양.** 확장 모듈은 원래 소스를 자기 네임스페이스에서 먼저 실행하고, 컴파일된 함수만 C 함수로
  바꾼다. 원래 함수는 `__typedpython_interpreted__` 에 남아 deopt 때 같은 전역·같은 클래스로 실행된다.
- **순서.** 스칼라 int/float/bool 과 컴파일된 함수끼리의 호출 → `list[float]`/`list[int]` 의 네이티브
  배열 → 고정 레이아웃 클래스.

### 4.3.1 안전성은 IR 에서 증명한다 (SPEC N-9)

사용자 결정: "IR 단계에서 안전성을 증명하도록 해". C 를 만들기 전에 `verify.py` 가 IR 에서 증명한다 —
정의 전 사용 없음, 노드 타입 일치, 비순수 함수에 deopt 노드 없음, 배열 접근은 경계 증명 또는 런타임 검사
유지, 배열 파라미터는 인덱싱·저장·len 만, OBJ 참조는 하나의 소유 규칙. **증명하지 못한 함수는 컴파일하지
않고** 인터프리터에 남기며 이유를 진단으로 낸다. 생성 C 는 `tp_runtime.h` 헬퍼로만 메모리와 `PyObject`
를 다룬다. 증명 밖의 안전망: ASan/UBSan, 인터프리터와의 차등 테스트, IR 수준 퍼징.

### 4.3.2 증분 컴파일 (SPEC N-10)

사용자 결정: "증분 컴파일도 지원하도록 해. 빌드 속도 너무 오래 안걸리게". 단위는 모듈. 키는 소스 해시 +
의존 모듈의 **인터페이스** 해시(타입 시그니처) + 컴파일러 버전 + 플랫폼 + 빌드 플래그. 본문만 바뀌면
인터페이스 해시가 그대로라 의존 모듈은 다시 컴파일하지 않는다. C 오브젝트는 모듈별로 캐시한다.
Gradle 태스크는 입력·출력을 정확히 선언해 up-to-date 판정과 빌드 캐시가 함께 작동한다.

### 4.3.3 고정 레이아웃 클래스 (SPEC N-11, M2b)

**레이아웃이 CPython 에서도 고정일 때만** 고정 접근으로 컴파일한다 — 사용자가 `__slots__` 를 직접 쓴 클래스.
컴파일러가 `__slots__` 를 몰래 더하면 `__dict__`·`vars()`·속성 추가가 CPython 과 달라지므로("같은 결과" 원칙
위반) 하지 않는다. binary-trees 벤치의 `Node` 는 그래서 `__slots__ = ("left", "right")` 를 소스에 적어야
컴파일되고, 그 변경은 모든 언어 열에 공평하게 적용되도록 벤치 소스 자체에 넣는다(CPython 기준선 재측정 필요).

- **필드 접근:** `type(x) is C` 로 가드된 값의 필드는 member descriptor 의 오프셋으로 바로 읽고 쓴다. 오프셋은
  모듈 초기화 때 클래스 사전의 descriptor 가 정말 member descriptor 인지 확인하고 잡는다. 값은 객체 그대로다.
- **순수성:** 슬롯 읽기는 사용자 코드를 실행하지 않으므로 효과가 아니다 — `check(node)` 같은 재귀 순회가
  순수 함수로 남아 i64 경로를 쓸 수 있다.
- **생성:** `__init__` 이 매개변수를 각 슬롯에 한 번씩 대입하기만 하면 `C(a, b)` 를 할당 + 슬롯 채우기로
  내린다. 그 밖의 `__init__` 은 객체 호출로 남는다.
- **메서드(예정):** `self` 를 `type(self) is C` 로 가드한 함수로 컴파일한다. 아직 구현 전이다.
- **IR (구현됨, #124):** `FieldGet`, `FieldSet`, `New`, `IsExact`, `CheckExact`, `Is`, `ClassDecl`, `Param.cls`.
  검증기는 정확한 타입 증명이 없는 필드 접근, 슬롯 밖 필드, 생성자 규칙 위반을 거부한다.
- **초기화 뒤 변경 (구현됨):** 슬롯 접근마다 정확한 타입과 클래스의 `tp_version_tag` 를, 생성마다 전역 바인딩을
  확인하고, 다르면 일반 경로(비순수) 또는 deopt(순수)로 간다. 세부는 SPEC N-11.

검토하고 기각한 경로:

- **Cython** — 사용자 결정으로 폐기(위).
- **mypyc** — 타입 체커가 mypy 에 묶여 있어 Pyrefly 와 판정이 갈라진다.
- **Nuitka** — 동작 동일성을 우선해 타입 특수화를 하지 않는다.
- **LPython** — 업스트림 활동이 LFortran 쪽으로 옮겨간 것으로 보인다.
- **Rust 생성** — 위.

### 4.3.3a 재귀 (SPEC N-8, #57)

호출 사이클(직접·상호 재귀)은 컴파일한다. 컴파일된 프레임에는 파이썬 프레임이 없으므로 모든 컴파일
함수의 진입에서 `tp_enter_call()`, 모든 출구(ok·error·deopt)에서 `tp_leave_call()` 을 부른다. 진입은
스레드별 컴파일 프레임 수에 현재 파이썬 프레임 깊이(`PyThreadState_GetFrame`/`PyFrame_GetBack`, 공개 API 만,
최상위 프레임 동일성으로 캐시)를 더해 `Py_GetRecursionLimit()` 와 비교하고, 넘으면 CPython 과 같은
`RecursionError("maximum recursion depth exceeded")` 를 낸다. 이어서 `Py_EnterRecursiveCall` 이 C 스택을
지킨다. **측정(3.13.0, 3.14.7, 기본 한도 1000):** 인터프리터와 컴파일 재귀 모두 같은 깊이(997)에서
실패하고, 인터프리터 프레임 k 개 위에서 컴파일 재귀를 시작해도 `최대 n + (추가 프레임 수)` 가 일정해
오프셋이 없다. 오프셋이 생기는 곳은 둘이다. (1) 한도를 C 스택이 먼저 닫을 만큼 올리면(예: 100만) C 가드의
메시지가 나온다 — 3.13 은 `maximum recursion depth exceeded in compiled code`, 3.14 는
`Stack overflow (used 8144 kB) in compiled code` — 인터프리터는 같은 한도에서 파이썬 한도 메시지를 낸다.
(2) 카운터는 모듈별(헤더가 `static`)이라, 한 컴파일 모듈의 두 프레임 사이에 **다른** 컴파일 모듈의
프레임이 끼면 그 프레임은 세지 않는다. 테스트는 두 경우 모두 "둘 다 예외를 내고 죽지 않는다" 만 단언하고
깊이를 기록한다(`test_recursion.py`).

### 4.3.4 객체 비용: 가상 객체, refcount 생략, 영역 할당 (SPEC N-12, 설계)

사용자 지시 (2026-10-03): "Rust 쪽으로 더 가는 방법을 적용하되 cpython과 동일성을 보장할 방법을 찾아."

**왜 필요한가.** 숫자·배열 코드는 이미 Rust 근처다(nbody 31x, Rust 의 약 2배). 객체가 많은 코드는 그렇지
않다. binary-trees 는 1.7x 인데, 컴파일된 코드도 노드마다 CPython 할당(`tp_alloc`: 0 채우기, GC 헤더,
GC 추적), refcount 증감, 해제(`subtype_dealloc`)를 그대로 치르기 때문이다(#125, 아직 프로파일로 확정 전).
더 가려면 객체를 아예 만들지 않거나(가상 객체), 증감을 빼거나(refcount 생략), 한꺼번에 할당·해제해야
한다(영역 할당). 셋 다 `id()`, `__del__` 시점, `gc` 관측과 부딪칠 수 있다.

**동일성의 정의.** 컴파일된 코드의 모든 실행은 **어떤 유효한 CPython 실행과 구별할 수 없어야 한다.**
구별은 관측으로만 할 수 있으므로, 설계는 "관측 지점" 목록과 "관측 지점에 닿기 전에 실제 객체로 되돌린다"는
규칙으로 이루어진다. CPython 자체가 정하지 않는 것(스레드 전환 시점)은 CPython 이 고를 수 있는 실행 중
하나를 고른 것으로 본다. 컴파일된 코드는 GIL 을 놓지 않으므로, 컴파일 구간 안에서 다른 스레드가 끼어드는
실행은 생기지 않는다. 이는 CPython 이 그 구간에서 전환하지 않은 실행과 같다.

#### 가. 가상 객체 (부분 탈출 분석 + 지연 실체화)

PyPy·GraalVM 과 같은 방식이다. N-11 클래스의 객체를 PyObject 대신 C 구조체(필드 값만)로 두고, 관측
지점에 닿기 직전에 실제 PyObject 로 만든다(실체화). 실체화된 뒤로는 인터프리터와 같은 객체이므로 결과가 같다.

- **대상 클래스.** N-11 조건에 더해 `__del__` 이 없고 `__slots__` 에 `__weakref__` 가 없는 클래스만. 이 둘이
  있으면 객체의 죽는 시점이 사용자 코드로 관측된다. `base = object` 이고 슬롯이 고정이므로 weakref 는
  `__weakref__` 슬롯으로만 생긴다.
- **관측 지점(실체화 트리거).** 아래에 닿는 가상 객체는 그 직전에 실체화한다.

  | 관측 | 이유 |
  |---|---|
  | 함수 밖으로 반환, 전역·컨테이너·실객체 필드에 저장 | 컴파일 구간 밖에서 보인다 |
  | 미지 코드 호출의 인자, `id()`, 기본 `hash()`·`repr()` | 객체 자체나 주소가 드러난다 |
  | **살아 있는 동안 일어나는 모든 미지 코드 호출** | 인자로 넘기지 않아도 `gc.get_objects()`·`gc.get_referrers()`·`tracemalloc` 이 존재와 메모리를 본다. 그래서 그 시점에 살아 있는 가상 객체는 **전부** 실체화한다 |
  | deopt | 순수 함수의 deopt 는 인자부터 인터프리터로 다시 실행하므로 내부 가상 객체는 버리면 된다. 비순수 함수는 효과 뒤 deopt 가 없다(N-9) |

  `is`, `type(x)`, `isinstance` 는 관측 지점이 아니다. 두 가상 객체의 `is` 는 할당 지점 동일성으로 정적으로
  정해지고, 가상 객체와 실객체는 같을 수 없다. 타입은 정적으로 안다.
- **실체화 순서.** 할당 순서대로 만든다. `gc.get_objects()` 의 순서도 관측되기 때문이다. 실체화는 도달
  가능한 가상 그래프 전체를 만들고 필드를 채운 뒤 진행한다.
- **효과.** 가상 객체는 미지 코드 호출이 없는 구간에서만 산다. 트리를 만들고 바로 소비하는 코드(binary-trees
  의 `check(make(d))`)는 그런 구간이다. `print` 를 섞는 루프는 매 반복 실체화하므로 지금과 같다.

#### 나. refcount 생략

- 같은 객체의 증가·감소 쌍을 빼는 것은 **그 사이 내내 다른 소유 참조가 그 객체를 살려 둔다**는 것과
  **그 사이에 미지 코드 호출이 없다**는 것을 IR 에서 증명할 때만 한다. 감소가 0 에 닿을 수 있는 지점은
  해제 지점이므로 빼지 않는다.
- 첫 대상은 빌린 읽기다. 예를 들어 `check(node.left)` 는 지금 `FieldGet` 이 새 참조를 만들어 넘기고 돌아와
  놓는다. 바깥 객체가 소유되어 있고, 그 슬롯이 그동안 쓰이지 않고, 사용자 코드가 돌지 않으면 빌린 참조로
  넘길 수 있다.
- `sys.getrefcount` 는 호출로만 관측되고, 호출은 위 조건으로 막혀 있으므로 관측되는 refcount 는 늘 정확하다.
  다른 스레드는 GIL 때문에 그 사이를 보지 못한다. free-threaded 빌드는 범위 밖이다(이 모듈은 GIL 을 다시 켠다).

#### 다. 영역(arena) 할당

- 개수 상한이 있는 가상 객체는 C 스택에 둔다. 재귀 구조처럼 개수에 상한이 없는 가상 객체(`make(d)` 의 트리)는
  **활성(activation) 하나에 묶인 영역**에 할당하고, 그 활성이 끝날 때 한꺼번에 놓는다.
- **실객체는 영역에 두지 않는다.** CPython 이 실객체를 하나씩 해제하기 때문이다(`tp_free`). 영역에는 가상
  객체만 있고, 실체화는 영역 밖에 실객체를 새로 만든다.
- **수명.** 영역은 수명을 감싸는 가장 안쪽 범위(루프 한 반복 등)에 둔다. CPython 이 일찍 놓는 객체를 영역이
  함수 끝까지 붙잡으면 최대 메모리가 커진다. 그 차이는 `tracemalloc` 같은 관측에서 드러날 수 있지만,
  관측은 미지 코드 호출로만 일어나고 그 직전에 실체화하므로, 남은 차이는 프로세스 메모리 총량뿐이다.
- **할당 실패.** 영역 할당이 실패하면 CPython 이 그 할당에서 냈을 `MemoryError` 를 같은 지점에서 낸다.
- **함수 경계.** `make` 가 만든 트리를 호출자가 바로 소비하면, 호출자의 영역에 쓰는 `make` 의 변형을 따로
  만든다. 할당 지점 특수화이고, 공개 진입점(wrapper)은 늘 실체화한 객체를 돌려준다.

#### 라. 증명과 시험

- **증명(N-9 확장).** 검증기가 증명하는 것은 넷이다. 가상 객체가 영역·스택 밖으로 새지 않는다. 모든 관측
  지점 앞에 실체화가 있다. 생략한 refcount 쌍마다 살려 두는 참조가 있다. 영역 수명이 그 안의 모든 참조
  수명을 감싼다. 증명하지 못하면 N-11 경로(실객체)로 컴파일한다.
- **차등 시험.** 관측 연산을 일부러 넣은 경우를 인터프리터와 비교한다. 대상은 다음과 같다.
  - 가상 객체에 대한 `id()`, 기본 `hash`·`repr`.
  - 살아 있는 동안 부른 함수 안에서의 `gc.get_objects()` 수·순서, `gc.get_referrers`.
  - 호출 경계의 `sys.getrefcount`, `tracemalloc` 스냅샷.
  - 가상 객체와 실객체 사이의 `is`.
  - 생성 도중 `MemoryError`. 시험용 할당기 훅으로 일으킨다.
  - `__del__`·`__weakref__` 가 있는 클래스. 대상에서 빠지는지만 본다.
- **변형 시험.** 미지 호출 앞 실체화를 빼면 `gc.get_objects` 시험이 실패해야 한다. refcount 쌍의 살려 두는
  참조 조건을 빼면 해제 시점 시험이 실패해야 한다.

#### 마. 동일성을 지키려면 결정이 필요한 점 (사용자 결정, 리더 경유)

1. **GC 수집 시점.** CPython 3.12 이후 세대 수집은 GC 추적 객체 할당 수로 예약되고, 다음 eval breaker 검사에서
   실행된다. 가상 객체는 할당되지 않으므로 수집이 늦어지거나 빠진다. 그러면 **다른 곳의** 순환 쓰레기의
   `__del__`, weakref 콜백, `gc.callbacks` 가 실행되는 시점이 옮겨간다.
   - (a) 지키는 방법: 가상 객체를 만들 때마다 GC 할당 카운터를 실제 할당과 같이 올리고, 수집이 예약되면 그
     자리에서 실행한다. 둘 다 CPython 내부 구조체(비공개 API)를 쓴다. 임베디드 CPython 판이 고정이라 가능은
     하지만 판이 바뀔 때마다 다시 확인해야 한다.
   - (b) 범위 밖으로 두는 방법: 언어 레퍼런스는 수집 시점을 구현이 정하도록 허용하고(데이터 모델 §3.1),
     CPython 도 3.13→3.14 에서 증분 GC 로 바꾸며 시점이 달라졌다.
   - **결정 (2026-10-04, 사용자): (b).** GC 수집 시점은 동일성 범위에서 뺀다. 그 밖의 모든 관측은 정확히 지킨다.
2. **이미 있는 차이: eval breaker 를 검사하지 않는다(N-8 부터).** 컴파일된 코드는 루프 안에서 eval breaker 를
   보지 않는다. 그래서 긴 컴파일 루프 동안 넷이 미뤄진다: 시그널(`KeyboardInterrupt`), 예약된 GC, pending
   call, **다른 스레드로의 GIL 넘김.** 앞의 셋은 시점 차이지만, 마지막은 다른 스레드가 굶는 동작 차이다.
   루프 뒤 간선(back-edge)과 호출에서 eval breaker 를 검사하면 고쳐진다.
   **1단계 구현 (#141):** 루프와 함수 진입에서 폴링하고, 일정 횟수마다 모듈의 `lambda: None` 을 불러 CPython 자기
   eval breaker 처리를 그대로 돌린다. 배열 copy-in·전역 스냅샷을 쥔 함수가 실행 중이면 미룬다. 그 함수 안에서의
   GIL 넘기기는 2단계(#154)이고, 방식은 결정 대기(#152).
3. **이미 있는 차이: 추적·모니터링.** 컴파일된 함수는 `sys.settrace`·`sys.setprofile`·`sys.monitoring`
   이벤트를 내지 않는다. 진입에서 추적이 켜져 있으면 인터프리터로 실행하는 방법(deopt 경로 재사용)을 제안한다.
   이것도 별도 이슈다.

이 셋은 N-12 이전부터 있는 경계도 포함한다. 1번이 결정되어 N-12 구현을 시작한다. 2번은 #141(1단계 완료), 3번은 #142.

### 4.4 Kotlin 경계의 직접 호출

이 플랫폼에서만 가능한 이점이다.

현재 Kotlin ↔ Python 호출은 `PyObject` 를 거친다. 실측 비용은 다운콜 데스크톱 약 260 ns,
업콜 데스크톱 약 550 ns, iOS 시뮬레이터 약 1.6 µs / 2.3 µs 다 (`docs/investigations/cost-table.md` 계열 측정).

그런데 **Kotlin 쪽 타입은 스텁 생성기(`PythonStubsTask`)가 이미 안다.** `compiled` 코드가 Kotlin 을
부를 때 양쪽 타입이 컴파일 타임에 확정되면, `PyObject` 마샬링을 건너뛰고 **C ABI 로 직접 호출하는
코드를 생성**할 수 있다. 경계 비용을 컴파일 타임에 지우는 것이고, CPython 을 임베드할 뿐인 모조는
구조상 할 수 없는 일이다.

**선행 조건:** 스텁 생성기가 픽스처 대역이 아닌 실제 `pythonx-map.toml` 을 읽고, 생성된 스텁이
IDE·타입 체커가 찾는 자리(pythonx-compose 배포본)에 설치돼야 한다. 2026-10 현재 미완료.

## 5. 등급 2 — 별도 언어 없는 GPU

### 5.1 하드 제약: AOT

**iOS 는 런타임 코드 생성을 금지한다.** torchnative `docs/design/DESIGN.md` 는 이 이유로 Triton 을
기각했다. Android 에도 인앱 GPU 컴파일러 툴체인이 없고, autotuning 워밍업은 짧은 세션에서 상각되지
않는다. 따라서 **GPU 커널은 빌드 타임에 컴파일된다.** JIT 은 데스크톱 개발 편의로만 허용한다.

### 5.2 커널 모델

Triton · NVIDIA Warp 처럼 파이썬 함수에 `@kernel` 을 붙인다.

- **처음에는 SIMT** (스레드 인덱스 기반). 컴퓨트 셰이더에 그대로 대응된다.
- 타일 추상화(Triton · cuTile 식)는 그다음.
- 커널 안: 고정 dtype 스칼라, 버퍼·텐서 뷰, 산술, 제어 흐름, 공유 메모리, 배리어.
  객체 생성·힙 할당·예외·파이썬 호출은 없다. 위반은 등급 1 과 같은 게이트에서 컴파일 에러.
- 커널 함수도 유효한 파이썬이다. CPU 에서 참조 구현으로 실행해 수치를 대조할 수 있다.

### 5.3 컴파일 경로

    @kernel 서브셋 → 자체 소형 IR → SPIR-V ─┬─ Vulkan (Android, 데스크톱)
                                            ├─ SPIRV-Cross → MSL (iOS, macOS)
                                            └─ naga → WGSL (웹)
                                  └──────────── PTX (데스크톱 CUDA, 별도)

한 소스에서 모바일·데스크톱·웹 타깃이 나온다.

### 5.4 착지점 — torchnative

컴파일된 커널을 **`torch.library` 커스텀 op 로 등록**하고 mps / vulkan 구현을 붙인다. 그러면
`transformers` 코드가 수정 없이 그 커널을 쓴다.

torchnative 의 설계는 이미 이 자리를 비워두고 있다. 융합 어텐션 같은 커널 계층을 "prefill 문제의
예정된 해법" 으로 지목했고, 커널 소스 후보로 손으로 쓴 Metal/NEON, CubeCL, AOT Triton 을 올려
두었다. TypedPython 등급 2 는 **같은 자리를 파이썬으로 채우는 네 번째 후보**다.

### 5.5 선례 — Taichi

파이썬 문법으로 Vulkan / Metal 커널을 AOT 컴파일해 모바일에 실었던 가장 가까운 선례다. 지금은
활동이 크게 줄었다. 기술보다는 **독자 런타임과 독자 생태계로 고립된 것**이 원인으로 보인다.
TypedPython 은 그래서 자체 텐서 런타임을 만들지 않고 **torch op 로 착지해 기존 생태계에 붙는다.**

### 6.1 단계 1 의 현재 상태 (2026-10-03, #16)

- **위치:** `python-multiplatform-ksp/src/main/python/typedpython/`, 테스트는
  `python-multiplatform-ksp/src/test/python/`. 사용자 지시("ksp랑 통합")에 따라 KSP 모듈 안에 둔다.
  KSP 프로세서는 Kotlin 심볼만 보고 파이썬 파일 변경으로는 다시 돌지 않으므로, **실행**은 1b 에서
  Gradle 태스크가 맡는다 — KSP 모듈은 소스와 배포(jar 리소스)의 자리다.
- **구현된 규칙:** SPEC N-7. Pyrefly 의 `Any` 유출 kind 6개를 에러로 올리고, Pyrefly 의
  per-expression 타입 리포트(`--report-pysa`)로 사용자 코드 안의 `Any` 식을 찾는다(`any-flow`).
  `cast()` 인자, 버려지는 식 문장의 값, 함수 시그니처 자체는 제외한다.
- **재할당·혼합 컨테이너 (#22):** Pyrefly 1.3.2 는 둘 다 보고하지 않고, 타입 리포트에 대입 대상의
  타입이 없다. 대신 이름을 *읽는* 위치의 타입은 기록한다. 그래서 대입문 바로 뒤에 같은 줄로
  `; x` 를 붙인 사본을 만들어(줄 번호 불변) 한 번 더 돌리고, 그 위치의 타입으로 판정한다. 두 번
  이상 대입되는 이름이나 컨테이너 디스플레이가 있는 파일에서만 돈다. `for` 대상과 컴프리헨션
  변수는 아직 탐침하지 않는다.
- **측정:** 1800줄 합성 모듈에서 plain `pyrefly check` 160–235 ms, 게이트 1.3–1.9 s — 두 번 잰 비율이
  모두 약 8배다. 탐침 패스를 별도 실행으로 붙이면 약 15배(232 ms → 3.6 s, load 41)였다 — 합성 모듈의
  `total += ...` 가 탐침 대상이라 두 번째 실행이 돌았기 때문이다. 지금은 탐침 대상이 있으면
  **탐침 사본(과 같은 검사의 나머지 파일)에 대해 Pyrefly 를 한 번만** 돌리고, 에러·`any-flow`·
  타입을 모두 그 한 번에서 읽는다(에러 열은 삽입 길이만큼 왼쪽으로 되돌린다). 같은 합성 모듈에서
  825 ms → 6.2 s, 약 7.6배(load 30 — 유효한 측정이 아니다. load 4 초과). 단독 측정이 아니다(두 번째는 load average 18.6). 절대값보다 비율을 기준으로 본다. 차이의
  대부분은 타입 리포트가 typeshed 사본까지 디스크에 쓰는 비용으로 보인다(추정, 미분해). 1b 에서
  빌드마다 돌리기 전에 줄일 대상이다.
- **고정:** Pyrefly `==1.3.2`. 타입 리포트는 Pyrefly 가 버전을 매기는 포맷이지 공개 API 가 아니다.

## 7. 위험

- **Pyrefly 의 외부 API 안정성.** 라이브러리 임베드는 확인 전까지 미룬다 (§4.1).
- **IR 이 표현하지 못하는 코드.** 게이트를 통과한 코드라도 IR 밖의 구문이 있으면 그 함수는 컴파일되지
  않고 인터프리터에 남는다(`Module.skipped`). 그 목록이 IR 확장의 요구사항이 된다.
  그 목록이 2단계 IR 의 요구사항이 된다.
- **등급 2 컴파일러의 규모.** 가장 큰 작업이다. 커널 하나를 끝까지 하는 것(§6 의 4)을 첫 검증
  단위로 삼아 범위를 제한한다.
- **기본 검사의 오탐.** 검사가 기본값이므로, 오탐 하나가 모든 사용자의 빌드를 막는다. 1b 를 켜기 전에
  이 저장소의 실제 사용자 측 파이썬 코드(`sample/`, pythonx-compose 의 소비 예시)에 게이트를 돌려
  에러 수와 그 원인을 기준선으로 박아 둔다.
- **서드파티 스텁 부재.** 스텁이 없는 의존성을 많이 쓰면 `Any` 출처가 늘어 에러가 잦아진다. 이 경우를
  에러로 둘지, 경계 한 곳의 명시적 캐스트로 해소하게 할지가 채택을 가른다.
- **파이썬 의미론과의 괴리.** 금지 목록이 실제 코드에서 얼마나 흔한지 측정해야 한다. 너무 흔하면
  `@compiled` 가 채택되지 않는다.

## 8. 미결 사항 (사용자 결정)

1. ~~`compiled` 의 표기~~ — **결정됨 (2026-10-03, 메인테이너):** `compiled` 는 **내장 이름**이다. 패키지
   아래에 두지 않고(`@typedpython.compiled` 아님) import 없이 `@compiled` 로 쓴다. 런타임은 임베디드
   인터프리터 시작 시 `builtins.compiled` 를 설치하고(#42), 일반 CPython 에서는 `typedpython` wheel 의
   `typedpython_builtins.pth` 가 `builtins` 에 없을 때만 항등 함수를 설치한다(런타임이 넣은 것을 덮어쓰지
   않는다). 타입 검사기에는 `__builtins__.pyi` 로 알린다 — Pyrefly 1.3.2 는 검색 경로의 그 파일을 추가
   내장으로 읽는다(실측). 모듈 단위 표기는 `# typedpython: compiled` 주석을 유지한다: `# pyright: strict` 와 같은
   도구 pragma 형태이고, 실행 시 이름 조회가 필요 없어 일반 CPython 에서 부작용이 없으며, 데코레이터 없이
   모듈 전체를 지정할 수 있다.
